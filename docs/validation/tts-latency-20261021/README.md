# 译音延迟优化验证（2026-10-21）

2026-10-22复核：本页为前轮1M版本归档，现行配置与连续六句测试见[长句验证](../long-speech-20261022/README.md)。早期批量JTAG读MMIO产生的串口计数不可靠，不能据下文旧记录确认2M物理帧错误；持续音频时的大块调试读取也会干扰服务。原数值与当时取舍保留，后续采用逐寄存器读取和结束后取证。

用户确认原译音效果可用，要求优化连续长句后半段约4–5秒的译音播出延迟；不以默认加速或降低音质换延迟。当前正式身份由 [NOW](../../context/NOW.md)维护，T2定义由 [TTS_SETTINGS](../../design/TTS_SETTINGS.md)维护。

## 采用的实现

- ARM TLS仍使用逐块确认的CIPSEND上传；TCP下行改为主动IPD接收，去掉逐次CIPRECVDATA/CIPRECVLEN往返。不使用UART透传。
- TLS明文按块交给WebSocket解析，保留分片、控制帧、边界检查；每轮最多处理2×2048字节明文，让UART、采音和DAC及时获得服务。ARM TCP上传保留64字节/轮预算，避免原主动模式8字节/轮使上传反而积压。
- 根据实际到包速度选择1.28秒或2秒音频预缓冲；慢到包仍保留2秒，发生空载后恢复2秒。完成的短响应直接播放，起播前仍先填足物理FIFO。默认1.0x、24kHz PCM、有符号采样顺序与音量处理未变。
- 正式保留1Mbaud（实际分频50）。启动探测等待完整OK行，识别所有受支持的易失波特率，避免切换诊断固件后沿用旧速率而初始化超时。只在会话开始前确认AT后清启动探测计数，运行期错误不清除。

## 未采用方案及边界

640ms预缓冲曾发生欠载；早期主动接收未限制TLS连续处理时曾UART溢出；2Mbaud变体曾出现运行期帧错误，均未作为正式配置。4KiB被动读取虽45段播放0欠载，但一段首末PCM出现约138秒停顿；不能说已解决4–5秒长尾，因此恢复旧2KiB被动后备参数，正式选用主动接收。该异常的云端/无线/TCP通知具体比例未被证明，不归咎于单一服务。

在相同到包回放中，这次约138秒异常的新旧最大等待都仍为138215ms；缓冲策略无法让尚未到达的数据提前播放，未从统计中隐去异常。不能把中位数改善写成所有长句尾音都减少相同比例。原ASR/定稿风险仍按原记录单列，本轮没有修改云错误恢复策略。

真实麦克风诊断版已就绪并持续上传，观察窗口内没有取得新译音，长句请求的听觉反馈尚未收到；不能引用前阶段“音量正常”作为本次长尾改善验收。最终无事件诊断正式版另做就绪观察：上传236→460页，USB供电1、CPU1心跳推进，网络/TLS/采样/显示错误均0。该窗口播放0次，样本0，不扩大验证范围。

若译音实际时长比连续输入长，1.0x播放仍会逐步排队；这与网络收包等待需要分别判断。本轮没有丢掉句子、静默截断译音或默认加速。完整声学P50/P95及真人长句尾部延迟仍待验证。
